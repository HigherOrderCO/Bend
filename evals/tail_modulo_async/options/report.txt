Independent and combined destination optimizations, 2026-10-20

Recommendation

Retain storage reuse as the simplest general candidate. Keep destination
specialization available as a measured alternative, not an unconditional
addition: combined with reuse it wins on matrix multiplication, but loses
some of reuse's radix benefit on Metal. Reject generic root-return inlining
and unbounded join forwarding. Bounded forwarding fixes the catastrophic
GPU regression, but adds runtime machinery for small, inconsistent gains.
No tested combination wins on every workload/backend.

selected.patch contains only storage reuse on top of the fused destination
prototype. It extracts node_alloc from ctr_build and uses that same helper
for the destination parent, before flushing the other spares. The existing
owned/static-node checks are preserved. It adds no new runtime field, tag,
return check, specialization pass, or dispatch rule to the fused prototype.
It is 22 tokens larger than that prototype, not hundreds of lines larger.

Experimental switches and implementations

All experiments start with BEND_DPS=1 and BEND_DPS_ASYNC=1. BEND_DPS_OPT is a
bitmask in phase1.patch and phase2.patch:
  1  reuse: retain a matching consumed node for the destination parent;
  2  specialize: clone entries called with a known destination, removing
     their destination-presence test and root-frame setup path;
  4  return: inline Dps~ret in WL_RETN, checking for its continuation id;
  8  join: on the last child, forward through completed constructor joins
     in a loop, reclaiming each record and retaining each completion fence;
 16  join_once (phase2): forward through at most one completed parent.

Phase1 tested base, fused, each of the four bits separately, and all=15.
Phase2 tested base, fused, reuse, reuse_spec=3, reuse_return=5,
reuse_spec_return=7, join_once=16, reuse_join=17 and all_once=23.
The second implementation factors ordinary delivery into a shared helper;
its one-parent path has no completion loop after constant folding.

Specialized ids use the compiler's name allocator. A regression fixture
uses even and even_dst: their generated names require disambiguation.
The initial naming implementation was corrected before the gates; all 24
phase1 benchmark C files remained byte-identical. Phase1 compiler timings
precede that correction; phase2 and final compiler timings include their
respective final implementations. Exact hashes are in metadata.json. phase1-measured.patch preserves the
historical compiler before the identifier-allocation correction; it is
provided for exact measurement reproduction, not as a recommended patch.

Runtime methodology

Full unchanged kmeans, tree-bitonic, tree-matmul and tree-radix inputs.
Five measured runs after one warm-up; variant order rotates and reverses.
Every timing run compares outputs. Times include whole-process startup.
CPU uses one/eight threads and --gpu off. Metal uses eight threads, 4 GB
spans for matmul/radix and 1 GB otherwise. Archives are built before timing.
CPU runtime, Metal runtime, compiler timing and instrumented profiling use
separate leased minis. Phase2 CPU workloads each have their own mini; all
variants of a given workload run serially on that same machine.

Hardware is Apple M4, 10 cores, 16 GiB; Apple clang 21.0.0, -O3 -std=c11.
Metal also uses Objective-C ARC, Metal and Foundation. hardware.jsonl lists
exact systems/toolchains. Earlier local CPU reports used clang 17, including
a different calling-convention configuration: their absolute times and
percentages must not be mixed with these new paired runs. An incomplete,
noisy local timing attempt was discarded. Reproduction smoke timings and
instrumented execution times are also excluded from performance summaries.
There is no thermal control; small differences are exploratory. CUDA and
interactive window/network demos were not benchmarked.

Individual changes and all four together

Elapsed-time change (%) relative to fused, within phase1; negative is better.
Complete times, ranges and all workloads/backends are in phase1/summary.json.

  variant                mat CPU1  mat CPU8  mat Metal  kmeans Metal  radix Metal
  reuse                       +2.7%      -0.2%      -5.7%      +1.3%      -2.2%
  specialize                  -0.4%      -1.1%      +0.4%      +1.6%      +3.8%
  return                     +13.2%      +9.8%      -0.9%      +1.7%      +4.0%
  join                        +0.4%      +0.7%      -1.3%    +702.8%      -0.1%
  all                        +19.9%     +11.7%      -5.8%    +684.4%      -0.9%

The unbounded join regresses kmeans from 0.4866 s to 3.9067 s on Metal,
about 8.03x elapsed time. All four together retain this regression and add
about 20% to single-thread matrix time. Correctness alone does not justify
retaining these transformations.

Combinations and bounded forwarding

Elapsed-time change (%) relative to fused, within phase2:

  variant                mat CPU1  mat CPU8  mat Metal  kmeans Metal  radix Metal
  reuse                       +2.1%      -1.3%      -4.3%      -2.2%      -3.1%
  reuse_spec                  -5.7%      -5.3%      -4.7%      -2.4%      +3.0%
  reuse_return                +9.9%      +6.2%      -3.8%      -1.2%      +1.7%
  reuse_spec_return          +19.3%     +10.6%      -4.0%      -2.5%      +0.1%
  join_once                   -0.3%      +0.8%      +1.1%      -1.1%      +0.7%
  reuse_join                  +1.6%      -0.9%      -2.2%      -4.0%      -1.6%
  all_once                   +19.3%     +10.4%      -2.1%      -1.5%      -1.5%

The bounded join returns Metal kmeans to 0.4893 s against fused 0.4950 s.
This supports avoiding the completion loop. It does not identify whether
the loop's hardware penalty comes from divergence, register pressure,
compiler lowering, or changed scheduling; no occupancy claim is made.

Reuse plus specialization improves matrix CPU time by 5.7%/5.3% and Metal
by 4.7% against fused. Its Metal radix time is 0.8724 s versus 0.8209 s for
reuse alone (about 6.3% worse), and 0.8473 s for fused. It is a real
workload tradeoff, not a universally better configuration. No
benchmark-name-specific switch or unmeasured arity heuristic was added.

Selected candidate

CPU numbers below are phase2 reuse: selected produces byte-identical CPU
assembly for all four programs under both local clang 17 and cluster clang
21. Metal numbers come from a separate final paired run of the simplified
candidate, the original fused compiler, and the original production compiler.
Each percentage compares against that run's fused control.

  workload           CPU 1 thread    CPU 8 threads    Metal
  tree-matmul                  +2.1%           -1.3%           -4.6%
  kmeans                       -3.1%           -3.6%           -0.5%
  tree-bitonic                 +0.2%           -2.6%           -4.3%
  tree-radix                   -2.9%           -3.0%           -2.0%

Reuse does not remove every regression: single-thread matrix multiplication
is still about 2-3% slower than fused on this toolchain, despite halving heap
allocator calls. Its eight-thread matrix result is near parity. Bitonic's
Metal variation changes sign between batches; the final -4.3% is not a
robust universal improvement. Matrix/radix Metal improvements are more
consistent across batches.

Profiling

Untimed instrumentation, separate binaries, one CPU thread. Counts include
actual heap_alloc/heap_free entry calls, explicit stack writes, generated
function/segment entries and root-return forwarding. These counters do not
measure CPU instructions or cache misses. The phase2 matrix profile also
counts executed destination-presence tests, including worker loop iterations.

                          fused          reuse          reuse+specialize
  heap allocations        244,669,839    125,578,383     125,578,383
  heap frees              244,669,839    125,578,383     125,578,383
  stack writes          5,235,850,887  5,235,850,887   5,235,850,887
  generated entries     3,815,571,348  3,815,571,348   3,815,571,348
  destination tests       244,669,056    244,669,056     121,335,936

Reuse removes 48.7% of matrix allocations/frees. Root-return fusion removes
121,335,936 generated entries, but checking the continuation on returns
costs more than those dispatches save in the measured CPU matrix runs.
All four workloads are profiled under every phase1 setting. The additional
phase2 matrix profiles cover every combination. Raw counters are retained. Phase1 profiles ran on a separate cluster mini
with clang 21; phase2 matrix counters ran locally with clang 17. All are
untimed semantic-operation counts, not hardware instruction measurements.
The one-thread profiles perform no direct parallel join forwarding; they
cannot explain the GPU join regression. No timings from these instrumented
programs are included in runtime medians.

Compiler speed and size

Seven workloads: the four benchmarks plus pure_par_sum, pure_par_sort and
pure_hvm5_mini. Seven measured repetitions after warm-up, rotating/reversing
variant order. Separate timers record compile_book only (after checking),
whole CLI Bend-to-C time, and native C compilation. Metal archive build times
are also recorded for each runtime binary, but those single samples are not
claimed as stable compiler-speed measurements. No language/checker changes.

Sum of per-workload medians for final fused -> selected:
  compile_book:       672.67 -> 679.99 ms   +1.09%
  whole Bend-to-C:  1,069.63 -> 1,073.08 ms +0.32%
  native compile:   2,237.96 -> 2,238.27 ms +0.01%
  generated C:     1,551,455 -> 1,551,052 bytes

The compiler data show no meaningful compilation speedup. Reuse is a small
shared allocation-helper change; cloning and return dispatch machinery are
not needed in the selected compiler. In phase1, specialization increases
aggregate generated C about 1.3% and native build time about 1%; enabling all
four raises aggregate native build time about 2.1%. Per-workload medians,
raw samples and code sizes are preserved, rather than only aggregate numbers.

Validation and status

Each of reuse, specialize, return, join, and all passes 1677/1677 gate tests.
Bounded join and all_once each pass 1678/1678 with the added name-collision
fixture. The simplified selected compiler also passes 1678/1678.
All 17 runtime benchmarks and 3 pure demos produce the recorded baseline
outputs under selected at one/eight threads: 40 checks, with source/C hashes
in final/coverage.json. Every CPU/Metal timing variant matches its peers.
All eight enabled phase2 variants finish the 100,000-node Metal chain.
Selected emits byte-identical C for that chain to the previously validated
fused version, whose measured worker stack is five words.

Production comp.ts and bend.ts remain unchanged. selected.patch is an
opt-in prototype, 67,369 tokens against the fixed 66,000 cap (1,369 over).
The cap was not changed. The experimental patches retain independent
switches for reproduction; the selected patch removes that experimental
machinery. The repository gate passes 54/54.

Reproduction

From the recorded production baseline, all work happens in temporary copies:
  python3 evals/tail_modulo_async/options/reproduce.py --phase phase1
  python3 evals/tail_modulo_async/options/reproduce.py --phase phase1 --backend gpu
  python3 evals/tail_modulo_async/options/reproduce.py --phase phase2 --variants fused,reuse,reuse_spec,join_once,reuse_join,all_once --threads 8
  python3 evals/tail_modulo_async/options/reproduce.py --phase phase2 --variants fused,reuse,reuse_spec --bench tree-matmul --mode profile
  python3 evals/tail_modulo_async/options/reproduce.py --phase selected --mode compiler --bench tree-matmul
  python3 evals/tail_modulo_async/options/reproduce.py --phase selected --backend gpu

--bench is repeatable and accepts the existing runtime benchmarks or pure
demos. --mode profile is host-only with one thread. Runtime and profiling
reproduction paths were exercised on matrix multiplication; compiler mode
was exercised separately. Raw datasets and summaries live in phase1/,
phase2/, and final/. Compare within a phase and workload, not across machines
or collection sessions.
