Matrix multiplication regression diagnosis, 2026-10-20

The destination prototype changes the quad-tree addition paths around mul.
The eight-product mul burst itself does not match the constructor-tail
pattern. add and add4 do, as do gen, vgen, vadd and vadd2.

One-thread CPU, unchanged full benchmark, Apple M4, clang -O3 -std=c11,
GPU off. One warm-up and five measured runs per variant, rotating/reversing
order. No benchmark processes ran concurrently. Medians, seconds:

  baseline                         2.008252
  all eligible sites               2.279257
  only add                         2.198290
  only add4                        2.162615
  only gen                         2.018497
  only vadd                        2.011894
  only vadd2                       2.062447
  only vgen                        2.018044

Selective versions use the final destination prototype with this guard
inserted immediately before its Dps~put/Dps~ret creation:
  if (process.env.DPS_ONLY && process.env.DPS_ONLY !== sc.def) return false;
Both BEND_DPS and BEND_DPS_ASYNC are 1. sc.def identifies the source function,
so the add4 and vadd2 guards include their bodies fused into mul and mvm.
The remaining functions use the baseline lowering.

Separate untimed, instrumented runs count host WL_CASE entries:

                             baseline          all sites
  total entries             4,183,573,524     4,645,945,236  (+11.05%)
  add entries                 911,961,600       911,961,600
  mul entries                 920,350,080       920,350,080

Another pair of untimed runs counts explicit STK assignments, including
those in runtime stack macros:
  baseline                  5,806,776,711
  all sites                 7,728,969,735  (+33.10%)

Both kinds of instrumentation use thread-local u64 counters and print them
at process exit. The workload is run with --threads 1 --gpu off. The entry
counter is inserted after each generated WL_CASE(FID_...) line. For stack
stores, assignment lvalues STK(I) are replaced by:
  #define PUTSTK(I) (*(dp_writes++, &STK(I)))
Profile timings are not included in the performance measurements.

The extra work is visible in the lowering. For an add4 root whose four
children are leaves, the baseline resumes four continuations and runs one
constructor join (five control segments). The destination version runs four
generic Dps~put handlers, three pending-sibling continuations and Dps~ret
(eight control segments). Its sibling records also carry a destination, and
each child gets a separate two-word destination frame. Internal children can
reuse that frame and bypass Dps~put, which benefits deeper trees, but there
are many shallow four-way additions in this workload.

A further generated-C diagnostic inlines the destination store into the
leaf returns of add, vadd, gen and vgen. It checks whether STK(-1) is Dps~put,
writes r0 through STK(-2), pops the destination frame and returns zero values
to the next continuation. It preserves the existing destination frames.
Five-run medians in a fresh paired run:
  baseline                  2.013080
  full destination          2.271963
  inlined leaf store        2.220882
Removing that dispatch recovers only part of the regression. This is not a
complete fix or a new compiler patch: it leaves extra frame bookkeeping and
introduces a destination test at those leaf returns.

Every run above prints 3797651056. The findings identify an implementation
overhead and localize most of the timing regression to add/add4. They do not
separate cycle costs of dispatch, stack traffic, allocation order and code
generation. These new counters and selective timings are CPU-only; Metal
was not separately profiled in this follow-up.

No production compiler or benchmark source was modified.
