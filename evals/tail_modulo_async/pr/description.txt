Constructor tails currently wait for their children and then allocate/rebuild the parent. On sequential paths this retains constructor continuations down the recursive spine; on parallel paths results travel through the join before becoming constructor fields. This change allocates the parent first, lets children fill its fields, and reuses a consumed node when the existing ownership analysis permits it.

The selected implementation is destination passing with fused sibling continuations and owned-node reuse. It is enabled automatically in the C emitter; CPU, Metal and CUDA share the emitted runtime. The JS emitter and language/checker are unchanged.

**Draft / merge blocker:** `comp.ts` is 67,278 tokens against the permanent 66,000-token cap. The repository gate reports that failure; the cap has not been changed. Removing the experimental switches saved 91 tokens, but another 1,278 must be removed by simplification before merging. This PR preserves the measured design for review rather than claiming the size gate passes.

## Transformation

For an eligible constructor tail:

```text
left, right = f(a), g(b)
return Node(left, right)
```

the operational transformation is:

```text
parent = reuse_owned_node_or_allocate(2)
root = Node(parent)

sequential:
  publish root into the incoming destination, or save it in a root frame
  redirect the final child's destination to parent[1]
  save g's arguments and a continuation:
    parent[0] = returned_value
    tail-jump g(b)
  tail-jump f(a)

parallel:
  retain root in an ordinary join record
  launch f(a) with destination parent[0]
  launch g(b) with destination parent[1]
  return root only after both children complete
```

A unary constructor tail needs no sibling continuation: it stores the parent, updates the current destination and tail-jumps to its child. Self-tail calls become worker-loop iterations; cross-function tails use the existing tail-transfer machinery. Branching retains only pending sibling work. There is no subtree merging or shared scope-wide completion counter.

## Chosen design: all pieces

1. **Conservative eligibility in `emit_dps`.** The current segment and callees return one boxed value. The body is an unshared, non-native constructor whose boxed fields are exactly the call-result variables, once each and in order. Calls are statically known, have no explicit bang and no borrowed parameters. Constructor and argument arities leave room within `WIDE`. Everything else keeps the existing lowering.
2. **One allocation/reuse helper.** `node_alloc` extracts the existing size-class matching logic from `ctr_build`. Both ordinary constructors and destination parents use it. Arguments are captured and dead bindings processed before selecting a spare; selection happens before flushing the other spares. A possibly static node retains the existing `HEAP_OFF` check, so static storage is never overwritten. This adds no new ownership analysis or free list.
3. **Allocate before descending.** Each eligible tail constructs its parent reference before starting the children. Reused storage follows the same destination protocol as fresh storage.
4. **Packed sequential continuations.** A continuation word holds the 16-bit function id below a 40-bit heap destination. `WL_RETN` masks the id before dispatch. An existing destination is filled immediately and redirected to the final child's field. At an ordinary caller boundary, a two-word root frame saves the result root and its final destination. The compiler's existing function-id limit bounds the encoding.
5. **One root-return segment.** `Dps~ret` stores the final result into its destination and returns the saved root. Its returned value is captured as a segment input before `WL_OPEN` resets output registers.
6. **Fused sibling continuations.** Each pending sibling saves its argument words and one packed continuation word. That segment stores the preceding child's result and immediately tail-jumps to the sibling. There is no separate `Dps~put` frame or handler per child.
7. **Ordinary parallel joins remain the completion boundary.** The parent root occupies the first join payload slot; the following slots retain child tasks for the scheduler. A `TAG_DST` continuation identifies result delivery into the parent's field. `task_deliver` resolves that destination through the join's root, writes the result, and uses the existing release/acquire completion protocol. The ready join returns the root; a consumer never receives a partially filled tree.
8. **Small runtime surface.** The runtime adds one continuation tag, destination selection in delivery, and the return-id mask. `DPS_ASYNC` is emitted from segment reachability so the delivery branch can disappear when unused. It is not a user-facing switch. There are no cloned destination entries, per-return root checks, cascading joins, benchmark-specific rules or additional compiler pass.

## Tried and discarded

The four later optimizations—reuse, known-destination specialization, root-return inlining and cascading join completion—were profiled and timed individually and together. Further batches tested combinations and bounded forwarding. Comparisons below use each experiment's paired fused-DPS control unless stated otherwise.

| Attempt | Evidence and reason to discard |
| --- | --- |
| Shared scope/counter prototype | Added synchronization instead of making the sequential constructor tail a loop; severe Metal kmeans regression. Replaced by destination passing with ordinary per-fork completion boundaries. |
| Separate destination frames / `Dps~put` | Genuine destination passing, but extra frames and dispatches caused the early matrix regressions. Replaced by stores fused into sibling continuations. Those earlier timings used a different CPU toolchain and are not mixed into the final table. |
| Known-destination entry specialization | Alone was mixed. With reuse it improved matrix CPU1/CPU8/Metal by 5.7%/5.3%/4.7% against fused, but Metal radix was 6.3% slower than reuse alone. Adds cloned entries and compiler machinery; not chosen as a general default. |
| Root-return inlining into every return | Removed 121,335,936 matrix segment entries but slowed matrix CPU1/CPU8 by 13.2%/9.8%. The extra return-path work outweighed fewer dispatches. |
| Cascading completed joins | Metal kmeans went from 0.4866 s to 3.9067 s, about 8.0× slower. GPU occupancy/divergence was not measured, so the precise hardware cause remains unknown. |
| All four together | Matrix CPU1/CPU8 slowed 19.9%/11.7%; Metal kmeans retained a roughly 7.8× regression. |
| At most one parent forwarded | Removed the catastrophic kmeans regression (0.4893 s versus fused 0.4950 s), but other gains were small/mixed and required more runtime machinery. |
| Reuse + specialization + root-return inlining | Matrix CPU1 slowed 19.3% in the combination batch. Fewer destination tests/entries did not make it faster. |

Reuse alone is the selected additional optimization. No tested combination won on every workload/backend.

[Full experiment report](https://github.com/nicolas-abril/bend/blob/codex/tail-modulo-async-reuse/evals/tail_modulo_async/options/report.txt) includes individual/combinations tables, methodology, raw-data locations and the preserved experimental patches.
