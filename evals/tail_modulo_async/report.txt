Tail-modulo-async prototype experiment, 2026-10-20

Follow-up: destination/report.txt and destination.patch contain the replacement
with a destination-passing worker loop and direct parallel field writes.
This report and prototype.patch preserve the original scope-counter experiment.

The prototype produced a localized Metal improvement in tree-bitonic, a large
Metal regression in kmeans, and effectively unchanged CPU performance. It is
not suitable for general enablement in its current form. The production
compiler was restored; prototype.patch contains the final implementation and
its regression test. unbounded.patch preserves the first implementation.

Baseline revision: 99a3d5fb42455f5c9cc75a6c2c459b2cd0a06172
The baseline was copied before any compiler edits. SHA-256 hashes are recorded
in metadata.json. Neither bend.ts nor the benchmark/demo sources were edited.

The transformation recognizes parallel lets whose continuation consists of
one boxed constructor, with its fields exactly the child results in order.
It allocates the output first, supplies each child a destination field, and
uses a completion scope to keep the result inaccessible until all descendants
have finished. Recursive constructor-only forks can share that scope instead
of retaining an executable join at each level.

The existing scheduler still needs a temporary launch bundle. The bundle is
freed after dispatch; the child tasks still exist. This is not an elimination
of all task allocations. The optimization runs only when the scheduler is
expanding parallel work; sequential drain execution keeps its existing path.
Shared constructor families, borrowed arguments, non-boxed child results,
reordered fields, nested constructor continuations, and explicit child GPU
transitions use the original implementation.

The first version uses one counter per connected construction scope. The final
version starts a new scope when its parent has about 64 unfinished descendants.
The threshold is a relaxed heuristic, not a safety bound. The final version
also omits its runtime extensions entirely from programs without a reachable
transformed fork.

CPU measurements used an Apple M4, 10 cores, 16 GiB, Apple clang 17.0.0
(clang-1700.6.4.2), -std=c11 -O3, with 1 and 8 threads and GPU disabled.
Metal measurements used cluster-02, also an Apple M4 with 10 CPU cores and
16 GiB, and cc -std=c11 -O3 -DBEND_METAL=1 -x objective-c -fobjc-arc.
GPU archives were built before measurement. Both versions used the same GPU
span: 4 GB for tree-matmul and tree-radix, 1 GB for the other measured programs.
An initial attempt with 1 GB failed on the baseline tree-matmul; that attempt
was excluded and both versions were rerun with 4 GB.

All timings below are whole-process elapsed seconds, median of five runs
after a warm run, alternating baseline/prototype order. Full existing inputs
were used. Benchmark binaries ran serially on each machine; GPU measurements
ran on a separate mini. These were exploratory runs under normal machine
activity, without thermal control. Sources, flags and inputs were identical
within each comparison. Small percentage differences should be treated as noise.

Final bounded prototype:

                       CPU, 1 thread       CPU, 8 threads       Metal
                       base -> prototype   base -> prototype   base -> prototype
  kmeans               2.052 -> 2.041       0.416 -> 0.416       0.618 -> 4.175
  tree-bitonic         6.084 -> 6.106       1.433 -> 1.435       1.732 -> 1.544
  tree-matmul           2.031 -> 2.043       0.482 -> 0.486       0.886 -> 0.885
  tree-radix            3.842 -> 3.847       0.729 -> 0.729       1.165 -> 1.173
  pure_par_sort         0.095 -> 0.096       0.060 -> 0.059       0.080 -> 0.081
  pure_par_sum          0.001 -> 0.001       0.001 -> 0.001       0.033 -> 0.033

The Metal tree-bitonic medians correspond to 1.12x speedup (10.9% less elapsed
time). Its individual samples vary and overlap, so this needs a longer
dedicated confirmation before being treated as a stable gain. The initial
unbounded trial also improved its median, by 1.09x. Kmeans is consistently
6.75x slower in the final version and 6.77x slower in the initial version.
Scope splitting did not fix that regression.

CPU peak RSS did not show a useful reduction. For example, 8-thread radix
measured 653.17 MiB baseline and 652.73 MiB prototype. GPU RSS in the raw records
is host-process RSS, not a measurement of peak GPU allocations.

Coverage and validation:

* All 17 runtime benchmarks and all 3 pure demos were compiled with both
  compilers. Their full-size CPU outputs matched. The unbounded version was
  checked with 1 and 8 threads; the final version checked all 20 at 8 threads
  and repeated the six tabulated cases at both thread counts.
* Eligible static fork sites were found in kmeans (1), tree-bitonic (1),
  tree-matmul (6), and tree-radix (3). The remaining benchmarks and pure demos
  had no eligible sites. The interactive window and network demos were not
  benchmarked.
* All paired Metal outputs matched for the six tabulated programs.
* The final enabled prototype passed the full mini-cluster test gate:
  PASS: 1676 / 1676. The snapshot's shard script exported BEND_TMA=1 so remote
  compiler invocations actually enabled the experiment. This included the
  added tail_modulo_async.bend test, whose uneven leaf work must finish before
  its checksum can be observed.
* CUDA was not tested.
* After restoring the production compiler, the repository gate passed:
  PASS: 54 / 54. git diff --check passed.

A separate instrumented CPU run counted optimized forks without using those
timings in the performance results. On 8 threads:

  kmeans:       110868 forks, 77538 reused scopes
  tree-bitonic:   6660 forks,  6405 reused scopes
  tree-matmul:       0 forks,     0 reused scopes
  tree-radix:    49152 forks, 48895 reused scopes

Thus static opportunities do not imply runtime activation: matrix
multiplication's eligible calls ran under the sequential drain. This also
limits how much CPU benefit this particular prototype can deliver.

To investigate kmeans, a diagnostic retained the new runtime helpers and
dispatch checks but emitted no transformed forks. Three measured Metal runs
gave medians of 0.648 seconds baseline and 0.651 seconds diagnostic, with
matching outputs. The large regression therefore depends on the transformed
fork code or its effect on the generated kernel, rather than merely having
the helpers present. This does not distinguish scheduling/allocation costs
from Metal compiler/register-pressure effects. No exact root cause is claimed.
The transformed operation is szip, which repeatedly merges small depth-3
statistics trees.

The original compiler is 65916 / 66000 ttok, leaving 84 tokens. The final
prototype is 67132 tokens, exceeding the cap by 1132. The cap was not changed.
Because this is a mixed-result experiment with a large regression, no unrelated
compiler refactoring was performed to make room for it. Neither patch is ready
to merge under the current cap.

To reproduce in isolated temporary directories on this baseline:

  python3 evals/tail_modulo_async/reproduce.py --threads 8
  python3 evals/tail_modulo_async/reproduce.py --threads 1
  python3 evals/tail_modulo_async/reproduce.py --backend gpu
  python3 evals/tail_modulo_async/reproduce.py --backend gpu --unbounded

Use --bench NAME repeatedly to select benchmarks or pure demos, and
--repetitions N to change repetition count. The runner checks the baseline
compiler hash, applies the selected patch only to a temporary copy, builds
both versions, checks every paired output, and preserves all results there.
The runner was exercised on both a control demo and the active radix case.

The research starting point was Tail Modulo Async-Await (ICFP 2026):
https://cambium.inria.fr/~yzakowsk/papers/tmca.pdf
This prototype adapts its destination/completion idea to Bend's existing wave
scheduler; it is not a complete implementation of the paper's calculus.
